Skrin 1 — Senarai Tawaran

class _ProgrammeListScreenState extends State<ProgrammeListScreen> {
  final _service = ProgrammeService();
  List<Programme> _programmes = [];
  bool _isLoading = true;

  @override
  void initState() {
    super.initState();
    _load();
  }

  Future<void> _load() async {
    final result = await _service.fetchProgrammes();
    if (!mounted) return;
    setState(() { _programmes = result; _isLoading = false; });
  }
}

Dalam build(): jika _isLoading → CircularProgressIndicator, jika tidak → ListView.builder.

Corak Hari 4: fetch dalam initState, setState bila data tiba, dan semak mounted sebelum setState dalam kod async.

Clean Code & Refactoring

Kod yang berfungsi sahaja tidak cukup — ia perlu boleh dibaca & diselenggara

  • Prinsip kod bersih dalam Flutter
  • Refactoring: sebelum → selepas
  • Demo aplikasi & sijil

Kod anda akan dibaca jauh lebih kerap daripada ia ditulis.

Oleh rakan sepasukan, oleh penyelenggara akan datang — dan oleh diri anda sendiri 6 bulan dari sekarang.

Motivasi clean code: bukan estetika, tetapi kos penyelenggaraan. Projek pagi tadi ialah bahan latihan yang sempurna.

Penamaan Bermakna & Komen "Kenapa"

Nama menerangkan tujuan:

  • ✅ EntryCategory.accepts(applicant)
  • ❌ check(x)

Komen jelaskan kenapa, bukan apa:

// ❌ komen "apa" — kod sudah jelas
// tambah 1 pada kaunter
counter++;

// ✅ komen "kenapa" — jelaskan sebab
// Guna fallback tempatan supaya kelas
// boleh diteruskan tanpa internet.
return _fallback();
Komen "apa" cepat lapuk bila kod berubah; komen "kenapa" kekal berguna kerana ia merekod keputusan.

Widget Kecil & Tanggungjawab Tunggal

  • Setiap widget buat satu perkara — build() yang panjang = petanda perlu dipecahkan
  • Row dalam Column dalam Row dalam Padding… melebihi 3–4 lapisan → ekstrak sub-pokok ke widget berasingan
  • Contoh sebenar: CategoryPill, _ChoiceDropdown dalam application_form_screen.dart
  • SRP: satu kelas = satu sebab untuk berubah — ProgrammeService urus data, ProgrammeListScreen urus paparan
Buka projek rujukan dan tunjuk bagaimana widget kecil menjadikan setiap fail mudah dibaca sekali imbas.

const — Beritahu Flutter "Ini Tak Berubah"

const SizedBox(height: 12),
const Icon(Icons.school),
const Text(
  'eTT Mobile',
  style: TextStyle(fontWeight: FontWeight.bold),
),
  • Widget const dibina sekali — Flutter langkau rebuild yang tidak perlu
  • Lint prefer_const_constructors (dalam flutter_lints) mencadangkannya secara automatik — terima cadangannya
const ialah kemenangan prestasi percuma. flutter_lints sudah didayakan lalai dalam projek Flutter baharu melalui analysis_options.yaml.

Refactoring — Ubah Struktur, Kekal Kelakuan

  • Kenal pasti bahagian build() yang berulang atau > 15–20 baris untuk satu "konsep visual"
  • Cipta kelas StatelessWidget baharu; pindahkan kod, tukar rujukan induk kepada parameter constructor
  • Tambah const pada constructor baharu (dan di tempat ia dipanggil)
  • Ganti kod asal dengan pemanggilan widget baharu
  • flutter analyze + uji semula visual — kelakuan mesti kekal sama

Kerja pindah kod berulang begini pun sesuai diserahkan pada AI — "Ekstrak bahagian cip kategori dalam build() ini ke StatelessWidget bernama CategoryPill, kekalkan gaya sama" — kemudian sahkan paparan tidak berubah.

Definisi refactoring: mengubah struktur tanpa mengubah kelakuan. Latihan petang ini: ambil satu widget besar yang dibina pagi tadi dan pecahkan.

Sebelum → Selepas

❌ Sebelum — satu build() panjang:

  return Card(
    child: Column(children: [

          child: Column(children: [
            Text(universityName),
            Text(fieldOfStudy), // ...
          ]),

      ]),
    ]),

}

✅ Selepas — komponen kecil:

Widget build(BuildContext context) {
  return Card(
    child: Column(children: [
      ProgrammeHeader(programme: p),
      const SizedBox(height: 12),
      Row(children: [
        CategoryPill(category: p.category),
      ]),
    ]),
  );
}

Contoh penuh boleh jalan: hari-5/snippets/refactor_before_after.dart. Corak sebenar: ProgrammeCard & StatusBadge dalam lib/widgets/.

ProgrammeCard dan StatusBadge dalam projek rujukan diekstrak sebagai kelas berasingan dan diguna semula merentasi beberapa skrin — itulah hasil akhir refactoring yang baik.

Kenapa Ekstrak Widget, Bukan Kaedah _buildX()?

Kaedah _buildX()Kelas widget berasingan
RebuildDijalankan semula setiap kali build() induk dipanggilBoleh dilangkau Flutter jika const & tidak berubah
constTidak bolehBoleh
Guna semulaTerperangkap dalam satu kelasBoleh dipakai di mana-mana skrin
💡 Ini soalan temu duga Flutter yang popular — fahami sebabnya (skop rebuild, const, guna semula), bukan sekadar hafal.
Jawapan ringkas: prestasi (skop rebuild lebih kecil, boleh const) dan kebolehgunaan semula. Penjelasan penuh di penghujung fail snippet refactoring.
