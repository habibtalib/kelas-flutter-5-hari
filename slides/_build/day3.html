Analogi setumpuk kad: hanya yang teratas kelihatan. Semua navigasi Flutter dibina atas konsep stack ini, diuruskan oleh widget Navigator.

Dua Kaedah Asas Navigator

KaedahFungsi
Navigator.of(context).push(route)Tolak skrin baharu ke atas tindanan
Navigator.of(context).pop([hasil])Keluarkan skrin teratas — boleh sertakan nilai hasil untuk skrin sebelumnya

Perkenalkan kedua-dua secara konsep dahulu. Nilai pulangan pop akan digunakan bila borang perlu memberitahu skrin sebelumnya bahawa permohonan berjaya dihantar.

Named Routes — Navigasi Guna Nama


MaterialApp(
  title: 'eTT Mobile',
  initialRoute: '/',
  routes: {
    '/': (context) => const HomeScreen(),
    '/tentang': (context) => const AboutScreen(),
  },
);

// navigasi guna nama:
Navigator.of(context).pushNamed('/tentang');
Setiap kunci ialah nama laluan, nilainya fungsi WidgetBuilder. Berguna bila aplikasi membesar — banyak skrin, navigasi dari merata tempat, atau deep-linking kelak.

onGenerateRoute — Bila Laluan Perlukan Data


onGenerateRoute: (settings) {
  if (settings.name == '/detail') {
    final programme = settings.arguments as Programme;
    return MaterialPageRoute(
      builder: (_) => ProgrammeDetailScreen(programme: programme),
    );
  }
  return null; // laluan tidak dikenali
},

// hantar arguments bersama nama laluan:
Navigator.of(context).pushNamed('/detail', arguments: p);
Peta routes biasa tak boleh terima parameter. onGenerateRoute dipanggil dengan RouteSettings yang membawa nama laluan dan arguments sekali. Dalam skrin, arguments juga boleh dibaca melalui ModalRoute.of(context).

Named Routes vs push Terus

push terus (pilihan eTT Mobile)

  • Aliran linear: senarai → butiran → borang
  • Type-safe — tiada as Programme yang boleh gagal masa jalan
  • Paling ringkas untuk app kecil

Named routes bila…

  • Banyak tempat perlu navigasi ke skrin sama
  • Perlu URL / deep-link (cth. versi web)
  • Navigasi dikawal berpusat (cth. log analitik)

main.dart sebenar guna home: const HomeScreen() tanpa routes: — kenali kedua-dua corak, pilih ikut keperluan.

Jujur dengan peserta: projek kita guna push terus kerana hierarki navigasinya mudah dan linear. Named routes ialah alat yang mereka perlu kenal untuk aplikasi lebih besar.

Kitaran Hayat Controller: initState & dispose


@override
void initState() {
  super.initState();
  _country = widget.programme.country;
  _fieldOfStudy = widget.programme.fieldOfStudy;
  _choice1 = widget.programme.id;
}

@override
void dispose() {
  _nameCtrl.dispose();
  _icCtrl.dispose();
  _emailCtrl.dispose();
  _phoneCtrl.dispose();
  _academicCtrl.dispose();
  super.dispose();
}
initState mengisi nilai awal daripada widget.programme. Fail sebenar turut mengisi nama dan No. KP daripada ProfileProvider jika pengguna sudah simpan profil.

Kenapa dispose() Penting?

  • TextEditingController memegang sumber sistem — listener, buffer teks
  • Lupa .dispose() → bocor memori (memory leak) — controller kekal dalam ingatan walaupun skrin sudah ditutup
💡 Peraturan mudah: setiap Controller yang dicipta dalam State, mesti di-dispose().
Punca memory leak paling biasa dalam Flutter. Tanam kebiasaan: bila taip TextEditingController(), terus tulis pasangan dispose() sekali.

Lima Validator… Kerja Berulang

Borang ini perlukan validator untuk fullName, icNumber, email, phoneNumber & academicSummary — menulis semuanya dari kosong agak leceh, terutamanya regex IC & emel. Minta AI jana draf pertama:

tandatangan `String? Function(String?)` untuk TextFormField:

Kemudian uji kes tepi & jalankan dart analyze sebelum terima — draf pertama selalunya ada pepijat halus.

Momen sebenar untuk capai AI: kerja berulang dengan corak yang jelas. Tapi jangan terima buta-buta — slaid seterusnya tunjuk kenapa.

String? validateIcNumber(String? value) {
  if (value == null || value.trim().isEmpty) {
    return 'No. Kad Pengenalan diperlukan';
  }

Peraturan eTT Dalam Borang: Dropdown Berperingkat

  • Dua DropdownButtonFormField<String> — negara & bidang — saling bergantung (cascading)
  • Tukar negara → senarai bidang disusun semula
  • Tukar bidang → senarai pilihan universiti disusun semula
  • Pilihan lama yang tidak lagi sah mesti di-reset
💡 Inilah cara borang menguatkuasakan peraturan sebenar eTT: 1 negara + 1 bidang, sehingga 3 pilihan universiti dalam bidang itu.
Domain memandu reka bentuk UI: sebab peraturannya satu negara satu bidang, dropdown mesti berperingkat. Status kelayakan disemak kemudian oleh KPT dengan keputusan LAYAK atau TIDAK LAYAK.

Logik Cascading — Kod Sebenar


void _onCountryChanged(String? value) {
  if (value == null) return;
  setState(() {
    _country = value;
    final fields = _fields;     // bidang unik dlm negara baharu
    _fieldOfStudy = fields.isNotEmpty ? fields.first : '';
    _resetChoices();            // pilihan lama tidak lagi sah
  });
}

void _resetChoices() {
  final programmes = _choiceProgrammes;
  _choice1 = programmes.isNotEmpty ? programmes.first.id : null;
  _choice2 = null;
  _choice3 = null;
}
Semua mutasi berlaku dalam satu setState supaya UI rebuild sekali dengan keadaan konsisten. _onFieldChanged serupa — tetapkan bidang, kemudian _resetChoices.

Kalau Buntu Menyusun Logik Ini…

Logik "tukar dropdown A, dropdown B & C perlu susun semula" mudah tersilap kalau ditulis tergesa-gesa. Rangka dengan AI dahulu:


Saya ada tiga DropdownButtonFormField<String> berperingkat dalam satu
Form Flutter: negara → bidang pengajian → pilihan universiti (1-3).
Tukar negara mesti menyusun semula senarai bidang (pilih bidang
pertama automatik); tukar bidang mesti menyusun semula pilihan
universiti. Tulis _onCountryChanged, _onFieldChanged dan
_resetChoices yang panggil setState() dengan betul, dan reset
pilihan lama yang tidak lagi sah.

Semak dalam app: tukar negara, pastikan pilihan universiti lama benar-benar hilang — bukan kekal terpapar sedangkan sudah tak tergolong dalam negara baharu.

Cara semak output AI untuk logik UI: jalankan tingkah lakunya, bukan sekadar baca kod. Kes gagal klasik ialah nilai dropdown lama kekal walaupun senarainya sudah bertukar.

_submit() — Sahkan, Bina, Pulangkan


void _submit() {
  if (!_formKey.currentState!.validate()) return;

  final choices = <String>[];
  for (final id in [_choice1, _choice2, _choice3]) {
    if (id != null && !choices.contains(id)) choices.add(id);
  }

  final application = Application(
    id: 'ETT-${DateTime.now().year}-'
        '${DateTime.now().millisecondsSinceEpoch}',
    fullName: _nameCtrl.text.trim(),
    icNumber: _icCtrl.text.trim(),
    // …country, fieldOfStudy, universityChoiceIds: choices…
    status: ApplicationStatus.submitted,
    submittedAt: DateTime.now(),
  );
  Navigator.of(context).pop(application); // pulang ke skrin sebelumnya
}

setState() — Apa Sebenarnya Berlaku?


setState(() {
  _fieldOfStudy = value;
});
  • Kod dalam closure dijalankan serta-merta — pembolehubah state berubah
  • setState() beritahu Flutter: "data widget ini berubah, jadualkan build() semula"
  • Flutter panggil semula build() — widget ini sahaja, bukan seluruh aplikasi
Tiga langkah sahaja. Rebuild terhad kepada widget berkenaan — sebab itu Flutter kekal pantas walaupun setState dipanggil kerap.

Kenapa Wajib setState()?


// SALAH — data berubah, tetapi UI TIDAK rebuild
onChanged: (v) => _country = v,

// BETUL — data berubah DAN UI diberitahu untuk rebuild
onChanged: (v) => _onCountryChanged(v), // dalaman panggil setState()
  • Flutter tidak memantau pembolehubah Dart secara automatik
  • Tanpa setState(): nilai dalaman berubah, tetapi skrin kelihatan tidak berubah
Simptom klasik: "saya dah tukar nilai tapi UI tak update". Hampir selalu jawapannya — mutasi berlaku di luar setState.

Kitaran Hayat StatefulWidget


createState() → initState() → build()
        → …setState() → build() (berulang)…
        → dispose()
KaedahBila dipanggilKegunaan biasa
createState()Sekali, bila widget diciptaMencipta objek State
initState()Sekali, sebelum build() pertamaNilai awal, baca widget.xxx, mulakan controller
build()Setiap kali setState()Bina/lukis semula UI berdasarkan state terkini
dispose()Sekali, bila State dimusnahkan.dispose() controller, batal Timer/Stream
Empat peringkat yang perlu dihafal. createState mencipta objek State; selepas itu initState sekali, build berulang-ulang setiap setState, dan dispose sekali di penghujung.

Kesilapan Biasa setState()

KesilapanAkibatPembetulan
setState() selepas dispose() (callback Future lewat)Ralat masa jalanif (!mounted) return; sebelum setState()
setState() terus dalam build()Gelung rebuild tak terhinggaPanggil hanya dari handler (onPressed, onChanged)
Lupa super.initState() / super.dispose()Kelakuan luar jangkasuper.initState() baris pertama; super.dispose() baris terakhir

Empat perangkap yang setiap peserta akan jumpa cepat atau lambat. Baris pertama paling kerap muncul semasa menguji borang — slaid seterusnya tunjuk cara siasat.

Bila Jumpa setState() called after dispose()

Biasanya berlaku bila Future/timer selesai selepas pengguna sudah tutup skrin. Tampal jejak ralat (stack trace) kepada AI dan minta ia jelaskan:


Saya dapat ralat ini semasa menguji borang Flutter saya:
"setState() called after dispose(): _ApplicationFormScreenState…"
[tampal stack trace penuh di sini]
Jelaskan puncanya, dan tunjukkan di baris MANA dalam kod saya
semakan `if (!mounted) return;` patut ditambah.

Jawapannya hampir selalu semakan mounted — biar AI bantu kenal pasti baris tepat dalam kod anda, kemudian sahkan dengan menguji semula aliran yang sama.

Stack trace ialah input terbaik untuk AI — spesifik dan lengkap. Tabiat debugging ini akan digunakan sepenuhnya semasa projek mini Hari 5.
